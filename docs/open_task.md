| 10 | Should the site ship a forced 150% zoom, and by which mechanism? | `client/src/App.css`, `client/src/index.css` | Requested 2026-09-08: “can the next deployment start at a 150% zoom.” A page **cannot** set the browser’s own zoom control — that’s a user setting, off-limits to JS and CSS. Three approximations, none free: **(a) `:root { zoom: 1.5 }`** — one line, scales everything including `vw`-based type, now supported in all major browsers (Firefox 126+). **(b) `html { font-size: 24px }`** — the accessible, rem-native approach, but the CSS is only ~70% rem (≈440 rem vs ≈179 px values) and 15 `clamp()`/`vw` rules are viewport-driven, so px and fluid type would stay put while the rest grew — inconsistent output. Also needs `body { font-size: 16px }` (`App.css:55`) removed. **(c) `transform: scale(1.5)`** — rejected; breaks scrolling and layout bounds. **The shared catch:** at 150% a 1440px screen has a ~960px effective viewport, crossing the `min-width: 1000px` and `1080px` breakpoints — desktop visitors would land in the narrow layout. And visitors who already zoom get 150% *on top of* their own setting. Needs an owner call on whether the intent is “the design should simply be bigger” (→ rework the type scale, not a zoom hack) or “bigger for a specific screen/demo” (→ (a), accepting the breakpoint shift). | 2026-09-08 |
